# 长文本流程：标准模式与完整流程

**何时读**：SKILL.md 判定走标准模式或完整流程时读这份文件。快速模式和审改模式不用读。

## 两档对比

| | 标准模式 | 完整流程 |
|---|---|---|
| 适用 | 非文学的长文本（传记、评论、报告、论文、说明文），要"可用、准确"的质量 | 文学作品（小说、散文、戏剧、诗歌），以及用户要出版或发表级别的稿件 |
| 每块的 agent | 译者（翻译后自查润色）→ 双语审校（兼做查证），共 2 个 | 译者（同样自查润色）→ 盲编辑（**只提建议**）→ 双语审校（兼做查证，并逐条取舍编辑建议），共 3 个 |
| 额外 agent | 术语预扫 1 个；书目 1 个 | 同左；英译汉文学另有风格参考 1 个 |
| 规模估算 | 每 6000 字符一块，每块 2 个 agent | 每块 3 个 agent |

**实测**（DLB 卡波特条目，英文正文约 1.4 万词，切成 15 块，走完整流程）：共用约 52 个 agent，每个约 12 万 token。审校只找出 9 处 medium 问题，没有 high 级问题；改动主要来自盲编辑，每块约 35 处。对这类非文学文本，标准模式已经够用。

**标准模式实测**（DLB 勒古恩条目，规模相近，也是 15 块）：共用 32 个 agent，约为完整流程的六成。审校结果为 high 0、medium 4，译文里也没有"当……的时候"这类明显的翻译腔。收紧标注规则以后，待查证条目从上一篇的 115 条降到 18 条。

**盲评对照**（卡波特条目中的 3 块，用同样的规则分别走两档，盲评时不告诉评审哪份出自哪档）：三块都判标准模式略好，差距全在忠实性，每块大约差 1 分。原因是当时的盲编辑直接改写全文，看不到原文，会顺手加因果关系、改变评价强度、换成口语，比如把"她相信老派的爱情"之后接成"因此……"，把 rightly 弱化成"不无道理"；审校只抓回了其中一部分。所以现在的完整流程里，**盲编辑只提建议，由看得到原文的审校逐条决定采纳与否**。这样编辑能跳出原文句法的长处保留了，走样的建议则被挡在外面。

拿不准时用标准模式，交稿时告诉用户可以对某几章升级到完整流程。用户点名要"完整流程""出版级"时，照用户的要求。

```
提取 → 诊断 → 术语预扫（定术语表和全文梗概）→ [风格参考]
     → 各块并行：译者（自查润色）→ [盲编辑提建议，仅完整流程] → 双语审校（查证 + 取舍建议 + 自己的修正）
     → 应用修正 → 合并 → 交付
```

盲编辑加双语审校的分工是完整流程的核心：编辑只看译文，负责找出译入语不通顺的地方并**提出**改法；审校同时看原文和译文，负责找出遗漏和错误，并对编辑的每条建议**拍板**。两个角色不能合并，编辑也**不能直接改稿**。标准模式没有编辑这一步，所以审校更要严格。

## 1. 提取与分块

```bash
python "$SK/scripts/extract.py" "<file>" --chunk-chars 6000 --out work/blocks.json
```

- 依赖：`pip install python-docx ebooklib beautifulsoup4 pymupdf lxml`。如果装有 poppler 的 `pdftotext`，PDF 提取会优先用它。
- 纯文本或用户直接粘贴的内容不用跑这个脚本。
- 处理时 EPUB 按 spine 顺序读取，PDF 会去掉页眉页码，DOCX 保留标题层级和 *斜体*。
- 遇到 `EXTRACTION_EMPTY`（扫描版 PDF）就告诉用户需要先 OCR。OCR 产物如果是 MinerU 的 JSON，读取 `pdf_info[].para_blocks[].lines[].spans[].content` 即可。
- 把每块写成 `work/c01_src.md`、`work/c02_src.md`……，标题块写成 `## 标题`。

**先分清正文和非正文**。书目、参考文献、索引、版权声明、目录这类内容，不走逐块翻译流程：标题和栏目名译出来；书名、篇名保留原文，有通行中译名的在后面括注；出版信息（出版社、城市、页码、日期）原样保留。这部分交给一个 agent 一次处理完，不需要审校。

## 2. 术语预扫（长文本必做）

开一个 agent 通读全文（不翻译），产出：

1. `work/glossary.json`：人名、地名、机构名、作品名（书名、篇名、影视名）、核心术语，各附建议译名。有通行译名的用通行译名（作品名以最常见的中文版书名为准），没有的自己译，并标注 `"(暂译)"`。
2. `work/synopsis.md`：全文梗概，300 字以内，按块列出每块讲了什么。
3. 语域判断：一段话写进 `glossary.json` 的 `style_notes`。

有了术语表和梗概，各块就不再互相依赖，可以**并行**处理。

**流水式推进**：同时运行的 agent 保持在 6 个左右。某一块完成一个阶段，就立刻启动它的下一个阶段，比如译完就送查证、编完就送审校；同时补上一个新任务。不要等一整批都完成再进入下一阶段。

译名中有几个高频、关键的，在开始翻译前用一句话请用户确认；用户不在场时，按建议译名先做，交付时列出来。

- 给预扫 agent 写 prompt 时，**不要举你自己没把握的示例译名**，它会照抄。比如作品有多个中译本时，书名就可能有几种说法（The Dispossessed 有《一无所有》《失去一切的人》）。应该让 agent 自己去查，把几种说法都列出来。
- "(暂译)"标记只留在术语表里，**不写进译文**。交付时在 notes 里列出全部暂译条目。

## 3. 风格参考（仅限英译汉的文学作品）

只有在用户提供了同一作者已出版的中译本，或告诉了你本地译本存放的文件夹时，才做这一步。评论、研究、传记类的书不算译本。

- **没有译本**：直接进入下一步。
- **找到了**：开一个 agent 读 1–2 段，提炼 3–5 条与当前原文相关的**具体技法**（比如长句怎么断、对话怎么写、方言怎么处理），不要书评。写入 `glossary.json` 的 `style_notes`。

## 4. 译者 agent

```
你是专业的{DIRECTION}译者。文体：{GENRE}；语域与读者：{REGISTER}。

先读这些规则（用 Read 工具），翻译时遵守：
{REFERENCE_SECTIONS}   ← 当前方向的核心卡，加上核心卡触发表命中的专题小节，写完整路径 $SK/references/...

术语表（已定译名必须照用）：读 {GLOSSARY_PATH}
全文梗概（你译的是第 {N} 块）：读 {SYNOPSIS_PATH}

要求：
- 忠实优先：不增加意思，不减少意思，不改变情态、语气和评价的强度。
- 文化层面默认异化，语言层面按译入语习惯来。
- 保持格式：## 标题、* * * 场景分隔、*斜体*、诗行分行、书信和剧本的版式。段落与原文一一对应，不合并、不拆分段落。
- 中文用全角引号“…”‘…’，书名用《》；英文按原文体例。
- 引文出处、页码、年份这类括注原样保留。
- **difficult_passages 只登记真正拿不准、需要别人核查的地方**（词义、搭配、术语、专名），一般每块 0–3 条。只是想说明自己为什么这样译的，写进 notes，不送查证。
- 原文里明显的事实笔误（年份、人名拼写），按 SKILL.md 总立场第 7 条处理，并登记到 notes。
- 译完后，用核心卡的合并审校清单把译文自查润色一遍，再输出。（两档都要做。）

把译文写入 {DRAFT_PATH}，把 meta 写入 {META_PATH}，格式：
{"new_terms": {"names": {}, "places": {}, "orgs": {}, "works": {}, "terms": {}},
 "difficult_passages": [{"source": "...", "choice": "...", "reason": "...", "type": "lexical|term"}],
 "notes": [{"source": "...", "choice": "...", "reason": "..."}]}
最终回复只写一行：完成情况和 difficult_passages 的条数。

原文：读 {SOURCE_PATH}
```

让 agent 自己读写文件，不要把原文和译文塞进 prompt，也不要让它在回复里贴全文。这样主会话的上下文不会被几十块译文撑满。

## 5. 查证（并入审校）

两档都**不单开查证 agent**：把译者的 meta 交给审校，由审校顺带核查 difficult_passages（见第 7 节模板）。收紧标注规则以后，每块只剩 1–2 条；审校本来就要对照原文，查证由它顺手完成即可。

审校**先分诊再查**：读一下语境，译者的选择明显没问题的直接放行；只有真正可疑的才查词典或上网，方法见 SKILL.md "查证"一节。实跑经验是，译者标的条目里大约九成一读语境就能放行。

## 6. 盲编辑 agent（仅完整流程，不传原文，只提建议）

```
你是资深的{TARGET_LANG}编辑，正在看一篇{GENRE}译稿。你没有看过原文，这是有意的安排：只按{TARGET_LANG}本身的标准来判断。
**你不改稿，只提建议**：每条建议都会由一位看得到原文的审校逐条决定采纳与否。

先读：{EDITOR_REFERENCES}
   英译汉：core-e2c.md；sun-zhili-e2c.md §7（翻译腔四种病因的详解）；discourse-cohesion.md 第二部分
   汉译英：core-c2e.md；pinkham-chinglish.md 全文；c2e-structures.md
   另加核心卡触发表命中的文体小节

找这几类问题：句法上的翻译痕迹、对话是否像真人说话、节奏、搭配、语域一致、衔接与连贯。
- 只提有明确理由的建议，纯措辞偏好不提。一块大约 10–25 条为宜。
- 改法要**保持原意和分寸**：不要为了顺而加因果关系、改变评价强度、把书面语改成口语。你没见过原文，凡是会动到意思的改法，都在 reason 里说明"可能影响原意"。
- 读来像是理解错了的地方，type 写 doubt，只说明疑点，不给改法（replacement 留空）。
- 刻意简短、重复、冷峻或破碎的写法，不要提建议去磨平它。

语域：{REGISTER}
术语表：读 {GLOSSARY_PATH}（译名不要动）
译稿：读 {DRAFT_PATH}

把建议写入 {SUGGEST_PATH}：
[{"locator": "<译稿中唯一能定位的片段，10–30 字>", "replacement": "<建议改法；doubt 类留空>",
  "type": "translationese|collocation|rhythm|register|cohesion|dialogue|doubt", "reason": "<理由>"}]
locator 必须从译稿里原样复制，并且只出现一次。最终回复只写一行：建议几条，其中 doubt 几条。
```

## 7. 双语审校 agent（原文和译稿都给）

```
你是双语忠实度审校。你会看到原文和一份译文。你的任务是核对正确性，不是改文风。

先读：{CORE_CARD} 里的合并审校清单；如果加读了文体专题文件，只看那份文件清单里对应文体的那一节。

对照原文逐段核对，找出：漏译（句子、分句、插入语、列举项）、误译或意思反了、指代错误、
人物关系错误、数字和时间错误、比喻理解错误、情态和语气强度走样、评价的褒贬走样、术语表违规；
汉译英还要查删冗余时是否连同意思一起删掉了。

判断标准（孙致礼"忠实与叛逆"）：只标出无意的叛逆，即由误解、疏忽或没有理由的省事造成的问题。
有理由、处理得当的有意变通不算错误。纯文风偏好不要标。

术语表：读 {GLOSSARY_PATH}
原文：读 {SOURCE_PATH}
译文：读 {TARGET_PATH}
译者 meta：读 {META_PATH}。逐条核查其中的 difficult_passages，真正可疑的才查词典或上网（方法见 SKILL.md"查证"）；顺带确认 notes 里笔误的处理符合总立场第 7 条。
{SUGGEST_LINE}   ← 完整流程填："编辑建议：读 {SUGGEST_PATH}。对照原文逐条取舍：意思和分寸都没变、确实更通顺的，采纳（可以微调）；会加意思、减意思、改强度、改语域的，拒绝；doubt 类，核对原文后决定要不要改。"标准模式删掉这一行。

把**全部要应用的修改**汇总成一份清单，写入 {FIXES_PATH}（没有问题就写 []）。清单包括查证的修改、你采纳的编辑建议、你自己发现的问题：
[{"locator": "<译文中唯一能定位的片段，10–30 字>", "issue": "omission|mistranslation|reference|number|modality|style-loss|glossary|over-cut|lexical|editor",
  "severity": "high|medium|low", "replacement": "<改后片段，删除时为空字符串>", "note": "<理由；采纳的编辑建议写'采纳编辑建议'>"}]
locator 必须从译文里原样复制，并且只出现一次；**几条修改的 locator 不能互相重叠**，同一处有几个改动的，合并成一条。
完整流程另外把拒绝的建议写入 {REJECT_PATH}：[{"locator": "...", "reason": "<为什么拒绝>"}]。
最终回复只写一行：各级问题几条；完整流程另报编辑建议采纳几条、拒绝几条。
```

## 8. 应用修正、合并、交付

```bash
py -3 -I "$SK/scripts/apply_fixes.py" work/c01_draft.md work/c01_fixes.json -o work/c01_final.md
```

- 脚本逐条把 `locator` 替换成 `replacement`，再清掉汉字之间残留的空格。审改模式里用户的稿子如果带有"## 编辑备注"或 «待核» 这类标记，脚本也会一并清理。
- `locator` 找不到，或出现不止一次的，脚本不会替换，而是列在输出里：**不要猜**，自己对照上下文处理，处理不了的列给用户。
- 两档都是对译者的 `_draft.md` 应用审校汇总的修改清单。盲编辑的建议不直接应用，只有经过审校采纳、进入清单的才会生效。

各块按顺序合并成 `<原文件名>_zh.md` 或 `<原文件名>_en.md`，放在原文件旁边。另写一份 `<原文件名>_notes.md`，内容包括：
- 术语表里的关键译名，以及标了"暂译"的条目；
- 所有 high 级修正；
- 脚本处理不了的修正；
- 尚待用户决定的问题；
- 原文笔误清单（总立场第 7 条）；
- 完整流程另附：编辑建议共几条、采纳几条、拒绝几条。

交付时，在回复里简要说明用了哪一档、多少个 agent、有几处 high 级修正。

## 9. 术语表与续做

```json
{"source_title": "", "direction": "e2c|c2e",
 "names": {}, "places": {}, "orgs": {}, "works": {}, "terms": {}, "recurring_phrases": {},
 "voices": {}, "style_notes": "", "history": []}
```

- 各块 meta 里的 `new_terms` 合并进术语表。和已有译名冲突时，保留已有译名，把冲突告诉用户；用户确认要改时，在 `history` 里记下旧译名和新译名，以便回头修改前面的块。
- 每完成一个阶段就更新 `work/progress.json`（`{"stage": "...", "done": [...]}`），中断后从这里续做。
